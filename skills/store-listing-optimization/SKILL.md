# Store listing optimization

Improve the listing against the actual app and its acquisition data, then complete the requested level of work: analysis, proposed copy, saved edits, or authorized submission. A recommendation is not a saved change, and submission is not public availability.

## Establish the scope and baseline

Identify the app by name AND package/bundle/store ID. Check the selected developer account, store, release and listing. Preserve the active task when the user asks a side question or says “now this app”; change only the intended app.

Infer the requested action from the conversation and carry forward existing authorization. Analysis-only or proposed-copy requests do not authorize submission. An authorized correction should progress through its requested save/submission stage without asking again merely because there are several clicks. Budgets, legal acceptance, unrelated pending changes and additional release actions remain separate decisions. Follow the environment's actual approval rules.

Inspect all existing locales and inherited text before editing. Preserve locale identifiers: Spanish Mexico is not automatically Spanish Latin America. Apply equivalent messaging improvements to the requested language pair, using natural local phrasing. If a locale does not exist, report that fact; do not imply it was edited. Decide whether adding it is within the user's requested scope and verify the app language before promising it.

Read project instructions and current state if available. Record current field values and pending console changes before mutation. Use supported connectors first; otherwise use the available browser automation with fresh observations and observed controls. Do not bind the skill to one browser, old element numbers or a user's machine paths.

## Check the promise against the app

Use the published release, actual UI and maintained product documentation; inspect relevant implementation when a claim is uncertain. Distinguish unreleased source from shipped behavior. Code is supporting evidence, not proof of the installed experience.

Keep a small claim/evidence list for uncertain statements. Check offline prerequisites, supported languages, saving/sharing, educational exercises, ads, purchases, account requirements and asset attribution when relevant. Remove unsupported claims or leave them explicitly pending verification. Do not invent guarantees such as “safe for children”, ad-free use, learning outcomes, multiplayer or cross-device restore. Preserve required license attribution and material limitations.

When accessible, inspect acquisition and listing performance, source/country/language breakdowns, activity/retention, representative review text and concrete quality signals. Scale the analysis to the task; a wording correction does not require a full code or compliance audit. Separate technical issues needing a new binary from listing changes. Keep review replies and social posts out of scope unless authorized.

## Audit the presence, not only the description

When asked for a full store review or growth opportunities, read [store-capabilities.md](references/store-capabilities.md) and inventory the relevant console sections before concluding the audit. Inspect the public listing and requested store/account locales, including visual/video coverage, discoverability settings, ratings/reviews, audience destinations, experiments, promotion opportunities and attribution. Identify relevant conditional tools rather than assuming everything is enabled for every app.

Record tool/section, availability evidence, current use, applicable audience/objective, recommendation/priority, prerequisites/cost and success measure. Distinguish unavailable, not eligible, not configured, not applicable and not inspected. A sidebar item or “New” label does not prove usability. If access is missing, complete the public/available evidence and name the unverified sections; do not call the whole store audited.

Keep a text-only request text-only. Read-only discovery in a full audit does not authorize creating events, starting experiments, changing distribution/pricing/privacy, or paid campaigns. Within existing authorization, complete the requested corrections; otherwise deliver a prioritized opportunity plan. Reuse `store-screenshots` for actual media/page/test work with a concrete brief instead of duplicating its mechanics.

## Turn statistics into a decision

For a full optimization/low-downloads request, analyze store statistics before selecting changes. Read [measurement.md](references/measurement.md). Establish a recent baseline and a comparable earlier window; use a longer view when volume or seasonality warrants it. Segment by acquisition source and relevant country/language/device/version instead of treating a changing traffic mix as a copy failure. A narrow text request still needs only proportionate evidence.

Cover discovery, listing response, completed acquisition, return use and quality when available. Check data coverage, consent/suppression, delay and metric definitions; missing values are not zero. Store dashboards describe aggregate activity, not which feature a person used. If the decision depends on feature behavior, inspect existing authorized analytics/events or qualitative evidence; do not install tracking or change consent merely to fill a report.

For each proposed change, connect observed evidence → plausible explanation → action → primary success measure and guardrail → comparison method. Label hypotheses and missing evidence. Prioritize the measured bottleneck; valid outcomes include keeping the copy, improving acquisition targeting, or investigating app quality. Do not force a rewrite when the data supports a different intervention.

Use the platform decision guidance to select custom pages for audience/message fit, randomized optimization tests for a measured comparison, and asset libraries for resource reuse. The “New” badge is not evidence of recent launch, eligibility or expected uplift. Retrieve current official guidance, then hand configuration/production to `store-screenshots` with the audience, hypothesis, locales and measurement plan; do not duplicate its procedures.

## Draft, then edit for natural language

Lead the short description with the core activity and a concrete reason to choose the app. Keep the name unless evidence supports a useful change. In the full description, explain what users do before secondary features/settings. Use actual search vocabulary naturally. Avoid technical implementation details, keyword stuffing, unsupported rankings and generic claims.

**Use Humanizer for English and Humaniza for Spanish before saving or submitting final copy.** Resolve skills by their declared capability/name, including namespaced aliases such as `humanizer:humanizer` and `aiskills:humaniza`; do not hard-code installation paths. Open each applicable skill and follow its editing/verification procedure. If not installed, search available skills; identify the missing editor and perform an explicit manual style pass rather than claiming the skill ran or blocking unrelated work. The intent is plain, specific copy, not a promise of evading AI detection.

For Humaniza, run its deterministic scanner when available and judge reported hits in context; a legitimate technical term or a single ordinary connector is not automatically an error. For Humanizer, use its embedded mode for store-copy production. Apply user-requested tone and keep supported facts, counts, names and restrictions through both passes. Do not pad a field to fill its limit.

Count the final strings after editing, including spaces, punctuation and line breaks. Respect each field's actual unit and console counter; bytes and characters differ for accented text. Produce the same final strings for the saved artifact and console entry, without Markdown decoration leaking into plain-text fields. Verify that paired locales still make equivalent promises.

## Apply and verify the authorized result

Save each intended locale and inspect the persisted values. At a review/summary screen, compare the pending change list with the authorized fields. Do not submit unrelated drafts in a batch. If they cannot be separated, finish the independent edits and explain the exact batch conflict before requesting a decision.

Submit when authorized and verify the resulting state. Distinguish saved draft, ready to send, automated checks, submitted/in review, approved and publicly visible. If approval is asynchronous, report submission accurately; do not wait indefinitely or claim publication. With an uncertain response, check the current state before retrying the same action. Stop repeated mutations when the same failure persists; preserve the draft and report the concrete blocker.

For Apple fields locked on the live version, finish permissible edits and prepare the other text for the next version. Do not create/upload a binary, bump the app version or accept an agreement solely because this skill is active. Existing explicit authorization for those actions still applies.

## Record and hand back

When the user asks to save the analysis or update session notes, use the app's own project folder and existing documentation convention. Preserve earlier technical work. Keep private account data and the user's revenue out of public skill examples. Record exact final text by locale, counted lengths, evidence windows, action/state checked, baseline and prioritized next steps. Add a measurement date only when the change becomes publicly visible.

Close with what changed, which locales, observed review/publication state and any real blocker. For recommendations only, supply concrete proposed copy when recommending a text change, and label it as a proposal; a diagnosis may instead recommend keeping the text. For authorized implementation, do not end at a diagnosis or an unsaved draft. Suggest a focused next measurement or experiment, separating estimates from observed lift. Paid promotion needs its own audience/objective/budget authorization; views alone do not establish installs.
