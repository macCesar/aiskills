# Implementing with Tailwind CSS v4

## Identify the installed pipeline

Start in the application or workspace that owns the CSS build. Check its manifest and lockfile and, with dependencies installed, run `npm ls tailwindcss @tailwindcss/vite @tailwindcss/postcss @tailwindcss/cli`. Find the CSS entry, the templates or scripts that contain classes, and the command that produces the deployed stylesheet. Check the project's browser targets before proposing v4 features. Tailwind v4 targets Safari 16.4+, Chrome 111+, and Firefox 128+. Use the installed version's documentation if the project is still on v3. Treat an upgrade as a separate scope decision. [Compatibility](https://tailwindcss.com/docs/compatibility) · [v3 documentation](https://v3.tailwindcss.com/docs) · [Upgrade guide](https://tailwindcss.com/docs/upgrade-guide)

| Project | Where to implement and verify |
|---|---|
| Laravel Blade with Vite | Keep Blade markup in `resources/views/` and use the existing Vite entry, commonly `resources/css/app.css`. The Vite plugins include Laravel's plugin and `@tailwindcss/vite`. Import Tailwind from the CSS entry and ensure the layout loads the configured entry via `@vite`. Run the existing development command and production build. [Laravel with Vite](https://tailwindcss.com/docs/installation/framework-guides/laravel/vite) |
| Static HTML | Use the v4 `tailwindcss` and `@tailwindcss/cli` packages. Build the input CSS into a file linked by the HTML. Include any scripts or templates that contain literal class names in the scan. [Tailwind CLI](https://tailwindcss.com/docs/installation/tailwind-cli) |
| Existing PostCSS pipeline | Configure `@tailwindcss/postcss` in the existing PostCSS configuration, import Tailwind from the CSS entry, and run the project's build. [PostCSS installation](https://tailwindcss.com/docs/installation/using-postcss) |

In a v3 migration, audit the old directives, integration packages and config. In v4, `@import "tailwindcss";` loads the framework. A retained JavaScript config needs an explicit `@config` directive. Check visual changes in border and ring defaults, placeholder styling, shadows, radii, outlines and stacked variants. Compare rendered screens in both themes before handoff. [Upgrade guide](https://tailwindcss.com/docs/upgrade-guide) · [Functions and directives](https://tailwindcss.com/docs/functions-and-directives)

## Diagnose a missing production class

1. Confirm the installed major and recreate the production build with its actual working directory, entry and build command. In the browser, verify that the page loads that build's stylesheet and that the expected class appears in the rendered markup.
2. Inspect the source for the **complete literal class**. Tailwind scans plain text. In Blade, choose between full strings like `bg-emerald-100 text-emerald-900` and `bg-amber-100 text-amber-900`. Expressions such as `bg-{{ $statusColor }}-100` contain no complete candidate. In JavaScript and Alpine’s `x-bind:class`, use complete strings for each state. Put those literals in the Blade view or JavaScript file that Tailwind scans. [Alpine in Blade](10-native-components.md#use-alpinejs-in-blade)
3. Check whether the literal's file is in scan scope. Automatic detection skips ignored files and dependencies, among other sources. Use `@source` for an explicit source relative to the stylesheet, such as `@source "../views";` from `resources/css/app.css` when those views need explicit inclusion. Use `source("../…")` on the import to set a scan base or `source(none)` with explicit sources for a bounded build. Reserve `@source inline(...)` for intentional finite candidates with no discoverable literal.
4. Rebuild, inspect the emitted rule and its variant, and verify the computed style in a production preview. Test the actual state, theme or width if the class is conditional. If the rule exists but loses in the cascade, inspect the winning declaration and matching variants in DevTools. The order of utilities in the HTML `class` attribute does not decide the winner. Emit one utility per property for each state unless the cascade is intentional. [Conflicting utilities](https://tailwindcss.com/docs/styling-with-utility-classes#conflicting-utility-classes) [Detection and explicit sources](https://tailwindcss.com/docs/detecting-classes-in-source-files) · [State variants](https://tailwindcss.com/docs/hover-focus-and-other-states)

## Translate design decisions into CSS

- **Base styles.** Preflight resets browser margins, heading styles, list markers and borders. Restore the intended hierarchy and affordances in the interface. Check inherited placeholder contrast and remove the ordinary `hidden` attribute when the element should become visible. Preflight gives that attribute precedence over display utilities. Review legacy embeds and third-party widgets when introducing Preflight. The official layer imports allow integration without its base stylesheet when required. [Preflight](https://tailwindcss.com/docs/preflight)
- **Tokens.** Use the project's approved spacing, type and palette as a system. Declare `@theme` variables when they should generate utilities, for example `--color-action` for `bg-action`. Use ordinary custom properties for internal values. Keep the project’s color model and tokens. The book’s HSL palette method is a design technique, and Tailwind’s default palette uses OKLCH. When a theme variable references another property that should resolve where the utility is used, use `@theme inline`, as in the demo's palette. [Theme variables](https://tailwindcss.com/docs/theme) · [Colors](https://tailwindcss.com/docs/colors)
- **States.** Use variants such as `focus-visible:`, `disabled:`, and appropriate attribute variants to reflect actual native states. Pair color with visible text where state matters. Keep keyboard focus distinct from hover and use `motion-safe:` for optional motion. [State variants](https://tailwindcss.com/docs/hover-focus-and-other-states)
- **Themes.** Pick the project's supported theme mechanism. By default, `dark:` uses the system preference. A manual selector can redefine it with `@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *));`. When most changes are palette-level, switch semantic custom properties at the theme root and set `color-scheme` so built-in controls follow. Verify text, focus and controls in both palettes. [Dark mode](https://tailwindcss.com/docs/dark-mode) · [Color scheme](https://tailwindcss.com/docs/color-scheme) · [Visual guidance](06-dark-mode.md)
- **Layout.** Start with the unprefixed narrow layout. Use viewport variants such as `lg:` for page-level changes. Use `@container` and container variants like `@md:` when the module may sit inside panels of different widths on the same page. Pick the threshold where content stops fitting and confirm the reading and tab order at either side. [Responsive design and container queries](https://tailwindcss.com/docs/responsive-design) · [Visual hierarchy and layout](02-page-mechanics.md)
- **Custom styles.** Share tokens first. Use component styles for repeated field treatments and utilities for local composition. A CSS rule is appropriate when it communicates a state or native selector more clearly. Prefer an existing project pattern before adding another. [Utility classes](https://tailwindcss.com/docs/styling-with-utility-classes) · [Adding custom styles](https://tailwindcss.com/docs/adding-custom-styles) · [Native component examples](10-native-components.md)
- **Extending a project.** Use `@utility` for a reusable utility that should accept variants. Use `@apply` when an existing CSS selector needs to reuse utilities. A CSS module compiled separately can use `@reference` to access the main stylesheet’s definitions without emitting its styles again. Prefer the spacing and color tokens for repeated values. Use arbitrary values for genuine one-offs and CSS custom properties for runtime values. [Directives](https://tailwindcss.com/docs/functions-and-directives) · [Arbitrary values and inline styles](https://tailwindcss.com/docs/styling-with-utility-classes#using-arbitrary-values)
